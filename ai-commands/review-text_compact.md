# AI Command: Rewrite Text

与えられた文章を、**原文の言語・意味・事実・論理を維持したまま、読み手にもっとも伝わる文章へ再設計してください。**元文の文型、段落、情報順序、見出し、言い回しはテンプレートではありません。**元文は「保持すべき意味・事実・制約のソース」として扱い、必要なら構成から書き直してください。**

## 最優先事項

優先順位は次のとおりです。

1. 原文の言語を保持する
2. 原意・事実・論理を変えない
3. 読み手が重要なことをすぐ理解できる構成にする
4. 冗長さ、弱い導入、重複、回りくどさをなくす
5. 明快で自然な文章にする
6. 元の表現を残す

**6はもっとも優先度が低いものとします。**

原文の表現や構造を残すこと自体に価値はありません。より良い構成や表現があるなら置き換えてください。
ただし、**言語・意味・事実・論理は変更対象ではありません。**

## 言語の保持

**原文の言語を変更してはいけません。翻訳はこのタスクの対象外です。**

- 日本語の文章は日本語のまま書き換えます
- 英語の文章は英語のまま書き換えます
- その他の言語も原文の言語を保持します
- 複数言語が混在している場合は、その言語の使い分けも保持します
- 固有名詞、引用、専門用語など、原文で意図的に別言語が使われている箇所を翻訳しません
- ユーザーが明示的に翻訳を依頼した場合だけ、指定された言語へ変更します

文章の読みやすさを改善するためであっても、出力言語を変更してはいけません。

## Rewrite policy

### 意味は守る。構造は守らなくてよい

次のものは保持してください。

- 原意、主張、結論
- 事実関係
- 因果、条件、比較、例外などの論理関係
- 可能性、仮定、推測、決定事項の区別
- 必要な具体情報
- 原文にある担当、期限、依頼、責任、謝罪、拒否、約束、合意
- リンク、メンション、引用、脚注、表、図、コード、数式、識別子など、意味を持つ参照情報

一方、次のものは必要に応じて大胆に変更できます。

- 文の切り方
- 段落の切り方
- 情報の順序
- 導入と結論の位置
- 見出し
- 箇条書きと文章の使い分け
- 重複した説明
- 抽象表現と具体表現の配置
- 原文の語順、言い回し、文章リズム

**一文ずつ修正するのではなく、文章全体を一度分解してから再構成してください。**

## 構成原則

読み手が最短距離で理解できる順序を選びます。

典型的には、次のような構成を優先します。

- 結論 → 根拠 → 詳細
- 目的 → 依頼 → 背景
- 問題 → 影響 → 対応
- 主張 → 具体例 → 含意
- 現状 → 課題 → 次のアクション

ただし、形式的にこの順序へ当てはめる必要はありません。文章の目的に合わせて最適な構造を選んでください。

### 冒頭を強くする

前置きから始める必要はありません。

読み手が最初に知るべき内容がある場合は、それを冒頭に置きます。背景説明は、その理解に必要な位置へ移動してください。

「〜について説明します」「ここでは〜を見ていきます」「重要なのは〜です」など、内容を増やさない導入は原則として削除します。

### 1段落1テーマ

形式上の改行ではなく、意味のまとまりで段落を作ります。

各段落はできるだけ、

- 最初にその段落の要点を示す
- 続けて必要な説明や根拠を置く

という構造にします。

### インパクトは情報設計で作る

強調語や煽り表現を追加してインパクトを作らないでください。

代わりに、

- もっとも重要な情報を前に出す
- 強い事実や結論を単独で明確に述べる
- 不要な修飾や留保を減らす
- 長短の文を適切に組み合わせる
- 具体と意味づけを近づける

ことで文章に推進力を持たせます。

## 禁止事項

原文にない次の内容を追加しません。

- 事実
- 数値
- 固有名詞
- 根拠
- 判断
- 感情
- 問い
- 約束
- 期限
- 合意
- 責任
- 謝罪
- 運用変更
- 専門用語や独自の分類

「もっと説得力を出す」ために、原文にない論拠を補ってはいけません。

原文で未確定のものを確定事項に変えたり、確定事項を不必要に弱めたりもしません。

重大な意味変更につながり得る箇所、特に法的・契約的意味、責任、謝罪、拒否、約束について、原文から安全に再表現できない場合は原文を維持してください。

## 保護対象

次の内容は破損させないでください。

- URL
- Markdownリンク
- メンション
- 引用
- コード
- 数式
- 表
- 脚注
- 図表参照
- 固有の識別子
- 外部参照に使われる番号
- 明示的に指定された書式

引用部分の本文は変更しません。

## 文章品質

### 共通

- 主語、述語、修飾関係を明確にします
- 同じ内容を複数回説明しません
- 抽象語だけで済ませず、原文にある具体を活かします
- 不要な専門用語や複雑な言い回しを平易にします
- 根拠のない強調語を加えません
- 読み手が補えない論理の中間段階は削りません
- 逆に、読み手が容易に補える冗長な説明は削ります

### 日本語

- 自然で簡潔な日本語にします
- 敬体と常体を統一します
- 同じ語尾の連続を避けます
- 不要な体言止めを避けます
- 冗長な「〜を行う」を避けます
- 係り受けが曖昧な場合は、語順変更または文の分割で解消します
- 不要な「が、」による接続を避けます
- 日本語と英数字の間に意味のない半角スペースを入れません
- 日本語のコロンは原則として全角「：」を使います
- 文法的な働きが中心の「こと」「とき」「ため」「できる」「さらに」「あらかじめ」などは原則としてひらがなにします
- 外来語の長音は原則として「ー」で表記します。ただし、固有名詞・製品名・専門用語・確立した表記は保持します

### 英語

- 自然な米国英語を使います
- 3項目以上の並列ではserial commaを使います
- Em dashは補足に限定し、1文で複数回使用しません
- 範囲にはen dash、複合修飾語にはhyphenを使います
- 社外文書・技術文書では短縮形を避けます
- 略語は必要に応じて初出で展開します。ただし、原文で展開されていない略語を推測で展開しません
- 数値と単位の間は半角スペース、パーセントは詰めます
- 日付は原文の用途を損なわない範囲で `July 15, 2026` 形式にします
- 見出しは原則sentence case、スライドタイトルのみtitle caseとします
- 正式名称の大文字小文字は変更しません

### 学術・技術表現

- *in vitro*、*in vivo*、*de novo*、*ex vivo*、*in silico*、*in situ* などの学術ラテン語は、Markdown上で可能ならイタリックにします
- 遺伝子名、タンパク質名、ツール名、モデル名、配列、単位は原表記を保持します
- コード、差分、ログ、設定断片は必要に応じてコードブロックで示します
- インラインコード、コードブロック、数式、リンク先などの内容そのものは変更しません

### 技術文書・提案書・調査文書

- 新しい概念は、対象 → 差分・働き → 必要なら定義、の順で理解しやすく導入します
- 因果関係では、原文にある機構や成立条件を残します
- 複数要因を単一原因へ還元しません
- 例だけから一般化しません
- 推測、仮定、不確実性を維持します
- 「AI」「ツール」など広すぎる語で、原文にある具体的な対象をぼかしません
- 後で参照しない識別子や独自ラベルを持ち込みません
- 「重要なのは」「まとめると」など、具体情報を増やさない空句は削るか具体化します

### Markdown

- 見出し、段落、リスト、引用、コードブロック、表などのブロック要素は、前後を空行1行で区切ります
- 同一階層の単純な箇条書きの項目間には空行を入れません
- 既存のMarkdown方言、見出し形式、リスト記号、階層、番号体系、拡張記法を尊重します
- 新しい見出しはATX形式とします
- 順序や参照に意味がない見出し番号は新しく付けません
- コードブロック、インラインコード、リンク、表、引用、HTML、数式、コメントの内容を不用意に変更しません

### 対人文章

文章の目的と相手に求める行動を早い段階で明確にします。

伝達、確認、判断、依頼を混ぜず、読み手が「何が決まっていて、何をすればよいか」を把握できるようにします。

- 人格ではなく、確認可能な発言、行動、結果、認識差、手続を扱います
- 不要な非難、皮肉、威圧、罪悪感への訴え、意図や感情の決めつけを避けます
- 必要な責任、謝罪、拒否、異議、重大性は弱めません
- 事実、引用、推論、評価、提案を混同しません
- 断定、留保、推量の強さを原文の根拠に合わせます

### メール

メールでは、目的と相手に求める行動を冒頭で明確にします。必要に応じて、**用件 → 必要な背景 → 依頼・確認 → 補足**の順へ再構成します。元文の順序に従う必要はありません。

- 件名は簡潔かつ具体的にします
- 関係性に応じた挨拶や定型敬語を、簡潔さだけを理由に削りません
- 初対面かどうか、氏名の字形、過去の接点、日程を推測しません
- 原文にある担当、期限、推奨案は明確にします
- 面談提案では、面談の目的と日程調整・開催形式を分けて書きます
- 英語メールでは用件を冒頭2文以内に置きます
- 英語メールの日程には、原文で確認できる場合は曜日とタイムゾーンを明記します
- 署名を新しく生成しません

### 読み物としての長文

記事、解説、書籍原稿などでは、内容を変えない範囲で文章のリズムも改善します。

- 短い文と長い文を使い分ける
- 具体と意味づけを近づける
- 強い事実や結論を埋没させない
- 不要な説明を削り、文章を前へ進める

事実記録を物語化したり、原文にない感情、疑念、問いを演出として追加したりしません。

メール、議事録、契約、仕様書、手順書、短い業務文書には、明示的な指定がない限りこのリズム調整を適用しません。

## 実行手順

内部では次の順に処理してください。

1. 原文から、変更してはいけない言語・意味・事実・条件・論理・参照情報を抽出する
2. 読み手がもっとも理解しやすい情報順序を設計する
3. **元文を一文ずつ修正せず、その設計に基づいて文章を再構築する**
4. 原文と照合し、意味・事実・不確実性・責任関係が変わっていないか確認する
5. 出力言語が原文から変わっていないことを確認する
6. 最終的な文章として校正する

元文の構成が十分に良い場合だけ、その構成を残してください。

## 対象範囲

- 選択範囲がある場合は、その範囲だけを書き換えます
- 文書全体が対象の場合は、節や見出しを含めて文章全体を1つの情報構造として扱います
- 必要なら節の順序や見出しも変更できます。ただし、外部参照される番号、リンク、識別子などを壊してはいけません
- 目的、読み手、期待する行動は、原文または依頼から確認できる範囲で判断します
- 確認できない事項を推測で補いません

## 最終チェック

出力前に次を確認してください。

- 原文の言語を保持している
- 原意、事実、論理関係を変更していない
- 推測、仮定、未確定事項を断定へ変えていない
- 必要な条件、例外、具体情報を落としていない
- URL、リンク、引用、コード、数式、識別子などを壊していない
- 元文への表面的な追従ではなく、読み手にとって最適な構成になっている
- 変更した各文・段落・構造が、明瞭さ、論理、簡潔さ、流れのいずれかを実際に改善している

- 修正後の本文だけを出力してください
- レビューコメント、変更理由、前置き、補足は出力しません
- 実質的な改善がない場合は、原文をそのまま返してください
